## 一、能力建设全景总览

### 1.1 建设目标

构建从**关键参数感知 → 异常告警 → 诊断分析 → 趋势预测 → 批量运维 → 售后支撑**的光模块/光链路全生命周期健康管理闭环。

### 1.2 能力成熟度模型

```
Level 5 ─ 预测性维护（AI驱动故障预测、主动替换建议）
Level 4 ─ 趋势分析与健康评估（健康度建模、劣化趋势、风险分级）
Level 3 ─ 诊断与根因定位（标准化诊断、链路级根因分析）
Level 2 ─ 异常检测与告警（实时告警、事件关联、快照留痕）
Level 1 ─ 数据采集与感知（DDM参数采集、BER/FEC监测）  ← 当前主要所处阶段
```

## 二、分方向能力建设详细规划

### 2.1 关键参数感知

| 维度 | 内容 |
|------|------|
| **建设目标** | 实现光模块全量关键参数的实时采集与可视化展示 |
| **当前能力基础** | • 已具备基础光模块 DDM 监测能力<br>• 部分设备已补齐 BER/FEC 等高阶参数能力<br>• ⚠️ 待核查：是否已北向到 AmpCon |
| **当前短板** | • Lane 级状态感知不足（多通道光模块无法逐Lane监测）<br>• VDM 等高阶参数待补齐（如 PAM4 信号质量指标）<br>• 基础状态信息完整性不足，部分状态尚未被有效感知 |
| **模块侧建设重点** | • AI 光模块固件对齐 NVIDIA 方向，补齐 VDM 等高阶参数能力<br>• 模块硬件支撑"单通道异常不等于整模块失效"的能力 |
| **平台/设备侧协同** | • 设备侧补齐细粒度参数透传与查询能力（逐Lane、逐参数）<br>• 平台侧补齐高频采集、历史存储与趋势展示能力 |

**关键指标体系：**

| 参数类别 | 具体参数 | 采集频率建议 | 优先级 |
|----------|----------|-------------|--------|
| 基础DDM | Tx Power, Rx Power, Temperature, Voltage, Bias Current | 5min | P0 |
| 高阶质量 | BER (Pre-FEC/Post-FEC), FEC纠错计数 | 1min | P0 |
| VDM参数 | PAM4 Level, SNR, Skew, TDECQ | 5min | P1 |
| Lane级 | 每Lane的Tx/Rx Power, BER | 5min | P1 |
| 环境参数 | Case Temperature, 供电电压波动 | 15min | P2 |

### 2.2 异常状态告警与事件记录

| 维度 | 内容 |
|------|------|
| **建设目标** | 实现异常的早期发现、精准告警、完整事件链记录 |
| **当前能力基础** | • 已支持链路通断识别（待进一步确认覆盖度）<br>• 设备侧已支持基础 DDM 告警<br>• 平台侧已支持部分模块告警上报 |
| **当前短板** | • 事件记录不全且未分级（缺乏 Critical/Major/Minor 分级）<br>• 早期异常识别能力不足（仅在故障发生后才告警）<br>• 部分告警状态缺失（如 FEC 纠错率突增无告警）<br>• 快照与留痕能力不足（异常发生时无法保存现场） |
| **模块侧建设重点** | • 增强异常触发时的光模块 MCU 留痕能力（模块内部日志）<br>• 模块侧支持阈值越限主动上报 |
| **平台/设备侧协同** | • 设备侧补齐异常事件上报与状态联动能力<br>• 平台侧补齐事件留存、关联分析、快照展示能力 |

**告警分级建议：**

| 告警级别 | 触发条件示例 | 响应要求 |
|----------|-------------|----------|
| Critical | 链路Down、Post-FEC BER > 阈值、Rx Power 丢失 | 即时通知，自动工单 |
| Major | Pre-FEC BER 持续升高、温度超限、FEC纠错率突增 | 15min内通知 |
| Minor | 参数接近阈值、单Lane性能劣化 | 汇总报告 |
| Warning | 趋势性劣化（7天趋势预测将越限） | 周报/月报 |

### 2.3 基础诊断能力

| 维度 | 内容 |
|------|------|
| **建设目标** | 建立标准化、可复现的光链路诊断流程与工具 |
| **当前能力基础** | • 已具备基础参数读取能力<br>• 已具备简单异常判断能力（如 Rx Power 低于阈值） |
| **当前短板** | • 典型问题诊断能力不足（缺乏故障树/决策树）<br>• 标准化表达与对接能力不足（诊断结果无统一格式）<br>• 缺乏链路级端到端诊断（仅单端口级别） |
| **模块侧建设重点** | • 提升模块协议规范性，确保不同厂商模块数据的表现一致<br>• 模块侧支持内置自检（Loopback Test） |
| **平台/设备侧协同** | • 设备侧补齐链路侧协同诊断能力（双端联动）<br>• 平台侧补齐多层分析、诊断汇总与结果呈现能力 |

**标准诊断流程建议：**

```
故障现象
  │
  ├─ 链路Down ──→ 物理层检查 ──→ 模块在位? ──→ 光功率正常? ──→ FEC状态?
  │
  ├─ 丢包/CRC ──→ BER检查 ──→ FEC纠错率 ──→ 信号质量(SNR/TDECQ)
  │
  └─ 性能劣化 ──→ 趋势对比 ──→ 环境因素排查 ──→ 模块老化评估
```

### 2.4 趋势识别与健康评估

| 维度 | 内容 |
|------|------|
| **建设目标** | 建立光模块/光链路健康度模型，实现劣化趋势预判与风险分级 |
| **当前能力基础** | • 已积累部分实时运行数据<br>• 已具备一定健康度规则和评分基础 |
| **当前短板** | • 健康状态处理能力仍不统一（各设备/模块标准不一）<br>• 风险分级能力不足（无法区分"即将故障"和"轻微劣化"）<br>• 趋势识别能力不足（缺乏时序分析和预测模型） |
| **模块侧建设重点** | • 模块侧持续输出稳定、可用的运行数据<br>• 逐步形成健康状态基础标签，为平台侧健康评估与预测能力提供数据基础 |
| **平台/设备侧协同** | • 平台侧补齐建模、评分、排序与预警闭环能力<br>• 建立基线模型（同型号/同批次/同环境的正常范围） |

**健康度评估模型建议：**

| 健康等级 | 分数范围 | 含义 | 运维建议 |
|----------|---------|------|----------|
| 优秀 | 90-100 | 所有参数正常，无劣化趋势 | 正常巡检 |
| 良好 | 70-89 | 参数正常，存在轻微波动 | 关注观察 |
| 一般 | 50-69 | 部分参数接近阈值或有劣化趋势 | 纳入替换计划 |
| 较差 | 30-49 | 多项参数异常，劣化趋势明显 | 优先替换 |
| 危险 | 0-29 | 即将或已经影响业务 | 立即处理 |

### 2.5 批量运维支撑

| 维度 | 内容 |
|------|------|
| **建设目标** | 支撑大规模光模块的批量状态拉取、固件升级、问题排查 |
| **当前能力基础** | • 已具备单模块监控能力<br>• 已具备基础的管理能力 |
| **当前短板** | • 批量采集能力不足（大规模场景下采集效率低）<br>• 批量识别能力不足（无法快速定位同批次问题模块）<br>• 批量排序能力不足（无法按风险/紧急度排序）<br>• 统一输出能力不足（缺乏批量报告导出） |
| **模块侧建设重点** | • 模块具备CDB升级功能，满足故障场景下的软件版本升级<br>• 模块支持批量固件查询与兼容性校验 |
| **平台/设备侧协同** | • 设备侧补齐规模化状态拉取与批量上报能力<br>• 平台侧补齐批量纳管、集中分析与统一治理能力 |

**批量运维场景矩阵：**

| 场景 | 触发条件 | 操作内容 | 预期产出 |
|------|---------|----------|----------|
| 批量健康巡检 | 定时/手动触发 | 全量模块状态采集+评分 | 健康度排名报告 |
| 问题批次定位 | 某型号/批次故障率异常 | 按批次/型号筛选+对比 | 问题批次清单 |
| 批量固件升级 | 新固件发布/漏洞修复 | 兼容性校验+分批升级 | 升级进度报告 |
| 预防性替换 | 健康度低于阈值 | 按风险排序+替换计划 | 替换优先级清单 |

### 2.6 返修筛查与售后支撑

| 维度 | 内容 |
|------|------|
| **建设目标** | 为光模块返修提供数据支撑，实现故障定责与售后证据链闭环 |
| **当前能力基础** | • 已可基于基础 DDM 和链路状态进行初步评估 |
| **当前短板** | • 标准化证据输出不足（缺乏统一的故障报告模板）<br>• 初步判断机制不足（无法区分模块故障 vs 链路故障 vs 环境因素） |
| **模块侧建设重点** | • 模块无此功能（当前模块侧无内置故障记录能力）<br>• 团队内提供更规范的异常记录与基础判断依据，为平台规则判定打下基础 |
| **平台/设备侧协同** | • 设备侧补齐日志与记录导出能力（支持导出模块运行历史）<br>• 平台侧补齐案例归纳、证据查询与售后支撑能力 |

**售后证据链建议：**

```
故障发生 → 自动快照（参数+环境+时间戳）
    │
    ├─ 模块侧证据：DDM历史、FEC统计、温度曲线、工作时长
    │
    ├─ 链路侧证据：对端状态、光功率对比、误码趋势
    │
    ├─ 环境侧证据：机房温度、供电状态、同框其他模块状态
    │
    └─ 综合判定 → 生成标准化故障报告 → 支撑返修/索赔
```

## 三、建设优先级与路线图

### 3.1 优先级排序

| 优先级 | 建设方向 | 理由 |
|--------|---------|------|
| **P0** | 关键参数感知 | 所有上层能力的数据基础，必须先行 |
| **P0** | 异常状态告警与事件记录 | 直接影响故障响应时效，客户感知最强 |
| **P1** | 基础诊断能力 | 减少人工排障时间，提升运维效率 |
| **P1** | 趋势识别与健康评估 | 从被动响应转向主动预防的关键 |
| **P2** | 批量运维支撑 | 规模化场景的效率需求 |
| **P2** | 返修筛查与售后支撑 | 商业闭环需求，降低售后成本 |

### 3.2 分阶段路线图

```
Phase 1（0-3个月）：数据基础建设
├─ 补齐 DDM/BER/FEC 全量参数采集
├─ 实现 Lane 级参数透传
├─ 建立告警分级体系
└─ 实现异常快照留痕

Phase 2（3-6个月）：智能分析能力
├─ 建立标准诊断流程与故障树
├─ 实现健康度评分模型
├─ 趋势分析与劣化预警
└─ 批量状态拉取与报告

Phase 3（6-12个月）：闭环运维体系
├─ 预测性维护（AI模型）
├─ 批量固件升级工作流
├─ 售后证据链自动生成
└─ 与工单系统/CMDB集成
```
