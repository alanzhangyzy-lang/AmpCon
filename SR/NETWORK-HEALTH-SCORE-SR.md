## 1. 背景与目标

### 1.1 背景

AmpCon 融合控制器管理三种网络场景（数据中心、园区、光传输），需要为每个 Site 提供 0-100 的健康度评分来反映网络整体运行状态。

### 1.2 目标

设计一套**维度扣分的健康度评分方案**，具备以下特点：
- 计算逻辑清晰，每个子项有明确的扣分规则
- 能反映异常程度和问题数量
- 三场景统一模型，差异仅在维度和子项

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| 三层计算 | 子项扣分 → 维度评分 → 站点健康度 |
| 并列检查 | 各维度独立计算，互不影响 |
| 扣分上限 | 每个维度最低 0 分，扣完为止 |
| 设备离线特殊处理 | 设备离线时，可用性维度为 0 分，其他维度不计算 |

## 2. 计算模型

### 2.1 三层计算架构

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 1: 站点健康度                                           │
│                                                              │
│   公式：健康设备数 / 总设备数 × 100                            │
│                                                              │
│   对齐 Cisco：Good 设备数 / 总设备数 × 100%                   │
│                                                              │
│   状态映射：健康(≥90) / 一般(70-89) / 异常(<70)               │
└─────────────────────────────────────────────────────────────┘
                              ↓ 下钻
┌─────────────────────────────────────────────────────────────┐
│ Layer 2: 设备健康度                                           │
│                                                              │
│   设备健康度 = 100 - Σ(各维度扣分)                             │
│                                                              │
│   判定结果：健康(≥90) / 亚健康(70-89) / 不健康(<70)            │
│                                                              │
│   对齐 Cisco：Good(8-10) / Fair(4-7) / Poor(0-3)             │
└─────────────────────────────────────────────────────────────┘
                              ↓ 下钻
┌─────────────────────────────────────────────────────────────┐
│ Layer 3: 设备问题详情                                         │
│                                                              │
│   展示：各维度的扣分明细和具体数值                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 站点健康度计算（对齐 Cisco）

#### 计算公式

```
站点健康度 = 健康设备数 / 总设备数 × 100
```

**定义**：
- 总设备数：站点下所有被纳管的网络设备
- 健康设备数：Layer 2 判定为"健康"的设备数量

**对齐 Cisco**：Cisco Catalyst Center 采用 `Good 设备数 / 总设备数 × 100%` 的计算方式，本方案与其一致。

#### 状态映射

| 评分区间 | 状态 | 颜色 | 运维建议 |
|----------|------|------|----------|
| 90-100 | 健康 | #10b981 绿色 | 正常巡检 |
| 70-89 | 一般 | #f59e0b 琥珀色 | 安排排查，非紧急 |
| 0-69 | 异常 | #ef4444 红色 | 立即处理 |

#### 计算示例

| 场景 | 总设备数 | 健康 | 亚健康 | 不健康 | 健康度 | 状态 |
|------|----------|------|--------|--------|--------|------|
| 正常运行 | 68 | 64 | 3 | 1 | 94 | 健康 |
| 轻微异常 | 68 | 50 | 12 | 6 | 74 | 一般 |
| 严重故障 | 68 | 20 | 18 | 30 | 29 | 异常 |

### 2.3 设备健康度计算（对齐 Cisco）

#### 计算公式

```
设备健康度 = 100 - Σ(各维度扣分)
```

每台设备根据以下维度独立评分，各维度扣分互不影响。

#### 设备维度固定分数

每个维度有固定的满分，所有维度满分之和为 100 分：

| 维度 | 满分 | 说明 |
|------|------|------|
| 设备可用性 | 20 分 | 设备是否在线 |
| 设备资源 | 20 分 | CPU/内存/温度 |
| 接口状态 | 20 分 | 接口Up率、错误率 |
| 协议状态 | 20 分 | BGP/EVPN/OSPF |
| 业务指标 | 20 分 | ECN/PFC/Buffer 等 |
| **合计** | **100 分** | — |

#### 子项分数池

每个维度的满分按子项权重分配给各子项：

```
子项分数池 = 维度满分 × 子项权重
子项扣分上限 = 子项分数池
```

**示例（设备资源维度）**：

| 子项 | 权重 | 分数池 | 扣分上限 |
|------|------|--------|----------|
| B-01 CPU 利用率 | 40% | 8 分 | 8 分 |
| B-02 内存利用率 | 40% | 8 分 | 8 分 |
| B-03 温度 | 20% | 4 分 | 4 分 |
| **合计** | 100% | **20 分** | — |

#### 角色权重

站点层面按设备角色配置权重，影响站点维度评分的计算：

| 角色 | 权重 | 说明 |
|------|------|------|
| Spine | 60% | 核心设备，故障影响大 |
| Leaf | 30% | 接入设备 |
| Server | 10% | 服务器（如有） |

**计算公式**：
```
站点维度评分 = Σ(角色设备平均维度评分 × 角色权重)
```

### 2.3 计算公式

**站点健康度**：
```
站点健康度 = Σ(站点维度评分_i)
每个维度满分固定，站点健康度满分 100 分
```

**站点维度评分**：
```
站点维度评分 = Σ(角色设备平均维度评分 × 角色权重)

其中：
角色设备平均维度评分 = Σ(该角色各设备维度评分) / 该角色设备数
```

**设备维度评分**：
```
设备维度评分 = max(0, 维度满分 - 子项扣分总和)
子项扣分总和 = Σ 子项扣分
```

**子项扣分**：
```
子项扣分 = min(子项分数池, 扣分计算值)

其中：
子项分数池 = 维度满分 × 子项权重
扣分计算值 = 按子项扣分规则计算
```

**设备离线时的特殊处理**：
```
设备离线 → 设备可用性维度 = 0 分，其他维度不计算
设备在线 → 所有维度正常计算
```

### 2.3 状态映射

| 评分区间 | 状态 | 颜色 | 运维建议 |

| 90-100 | 健康 | #10b981 绿色 | 正常巡检 |
| 70-89 | 一般 | #f59e0b 琥珀色 | 安排排查，非紧急 |

## 3. 业内竞争分析

### 2.1 厂商方案对比

| 厂商 | 产品 | 计算模型 | 优点 | 缺点 |
|------|------|----------|------|------|
| Cisco | Catalyst Center | 设备分类聚合（Good/Fair/Poor） | 模型简单直观，下钻路径清晰 | 三分类粒度较粗，无法反映问题严重程度差异 |
| Juniper | Mist AI | SLE 独立展示（不聚合） | 各维度独立，问题归因清晰 | 无单一健康度，运维人员需看多个指标 |
| Juniper | Data Center Assurance | 5 大 SLE + Classifier 分层 | 协议层监控细致，适合 DC 场景 | 模型复杂，学习成本高 |
| Arista | CloudVision | 合规性检查（Pass/Fail） | 检查项灵活，支持动态基线 | 合规性不等于健康度，无法反映运行状态 |
| 华为 | iMaster NCE-FabricInsight | 多维加权聚合 | AIDC 指标全面，支持 INT | 存在重复扣分，分数可解释性差 |
| 华为 | iMaster NCE-CampusInsight | 雷达图六维度 | 用户体验导向 | 六维度独立展示，无单一健康度 |
| 华为 | iMaster NCE-T | 光路健康占比 | 光传输专业性强 | 仅适用光传输场景 |
| 华三 | SeerAnalyzer | AI 预测性分析 | 预测能力强 | 健康度计算逻辑不透明 |

### 2.2 核心问题分析

#### 问题一：因果关系导致的重复扣分

| 场景 | 问题表现 |
|------|----------|
| 设备离线 | 产生 1 个 Critical 告警 + N 个接口 Down 告警，如果告警参与计算则重复扣分 |
| CPU 超阈值 | 可能导致 BGP 震荡，两个问题同时扣分 |
| 接口 Down | 必然产生告警，设备状态和告警同时扣分 |

**业内做法**：
- Cisco：隐式处理，Good/Fair/Poor 分类时不叠加告警
- Juniper：Classifier 分层，上层覆盖下层
- 华为：未处理，存在重复扣分

#### 问题二：模型演进不平滑

| 演进方式 | 问题 |
|----------|------|
| 设备分类 → 维度加权 | 计算模型完全改变，用户无法理解分数变化 |
| 增加检查项 | 模型不变，用户理解成本低 |

**业内做法**：
- Cisco：始终使用设备分类模型，增加 KPI 不改变模型
- Juniper：SLE 模型固定，增加 Classifier 不改变模型
- 华为：从简单版到专业版模型完全不同，演进不平滑

### 2.3 本方案的选择

| 对比项 | 本方案选择 | 原因 |
|--------|-----------|------|
| 计算模型 | 维度加权聚合（对齐 Cisco） | 各维度独立评分，逻辑清晰直观 |
| 因果处理 | 告警独立 + 设备离线特殊处理 | 对齐 Cisco，避免重复扣分 |
| 演进方式 | 增量增加检查项 | 保证演进平滑 |
| 场景区分 | 检查项按场景定制 | 模型统一，差异仅在检查项 |

**与 Cisco 对齐的关键点**：
1. **计算模型**：采用 KPI 加权聚合，各维度独立评分后汇总（非优先级递进检查）
2. **可达性处理**：设备离线直接判定不健康，其他维度不计算
3. **状态分类**：健康/亚健康/不健康 三分类，对应 Cisco Good/Fair/Poor

## 3. 检查项定义

### 3.1 维度一：设备可用性（满分 20 分，对齐 Cisco "可达性"）

每台设备根据以下维度独立评分，各维度扣分互不影响：

```
设备健康度 = 100 - Σ(各维度扣分)
```

**维度权重与扣分上限**：

| 维度 | 满分 | 扣分上限 | 说明 |
|------|------|----------|------|
| 设备可用性 | 20 分 | 20 分 | 设备是否在线（对齐 Cisco "可达性"） |
| 设备资源 | 20 分 | 20 分 | CPU/内存/温度（对齐 Cisco KPI 权重合计 40%） |
| 接口状态 | 20 分 | 20 分 | 接口 Up 率、错误率（对齐 Cisco "链路"权重合计 40%） |
| 协议状态 | 20 分 | 20 分 | BGP/EVPN/OSPF |
| 业务指标 | 20 分 | 20 分 | ECN/PFC/Buffer 等 |
| **合计** | **100 分** | — | — |

##### 与 Cisco KPI 权重对照

| Cisco KPI | Cisco 权重 | 本方案维度 | 本方案权重 |
|-----------|-----------|-----------|-----------|
| 可达性 | 最高优先级 | 设备可用性 | 20% |
| CPU 利用率 | 20% | 设备资源 | 20% |
| 内存利用率 | 20% | 设备资源 | （含于 20%） |
| 链路可用性 | 25% | 接口状态 | 20% |
| 链路错误率 | 15% | 接口状态 | （含于 20%） |
| 电源/风扇状态 | 10% | 设备资源 | （含于 20%） |
| 温度状态 | 10% | 设备资源 | （含于 20%） |

##### 设备状态判定标准

| 状态 | 分数区间 | 颜色 | 判定条件（对齐 Cisco） |
|------|----------|------|----------------------|
| 健康 | 90-100 分 | 绿色 | 所有维度正常（对齐 Cisco Good: 8-10 分） |
| 亚健康 | 70-89 分 | 琥珀色 | 部分维度扣分但未达到严重程度（对齐 Cisco Fair: 4-7 分） |
| 不健康 | 0-69 分 | 红色 | 任一关键维度严重异常（对齐 Cisco Poor: 0-3 分） |

##### 设备离线特殊处理

```
IF 设备离线 THEN
    设备可用性维度 = 0 分
    其他维度不计算（不产生扣分）
    设备健康度 = 0 分 → 不健康
ELSE
    所有维度正常计算
END IF
```

**说明**：此处理方式对齐 Cisco "可达性不可达直接判定 Poor" 的逻辑。

## 5. 子项扣分规则

### 5.1 维度：设备可用性（满分 20 分）

#### 子项定义

| 子项编号 | 子项名称 | 权重 | 分数池 | 数据来源 |
|----------|----------|------|--------|----------|
| A-01 | 设备在线状态 | 100% | 20 分 | ICMP/SNMP |

#### 扣分规则

| 条件 | 扣分 | 维度评分 |
|------|------|----------|
| 设备在线 | 0 | 20 分 |
| 设备离线 | 20 | 0 分 |

#### 计算公式

```
IF 设备离线 THEN
    设备维度评分 = 0
    其他维度不计算
ELSE
    设备维度评分 = 20
END IF
```

#### 数据采集要求

| 项目 | 要求 |
|------|------|
| 采集方式 | ICMP Ping 或 SNMP GetRequest |
| 采集频率 | 1 分钟 |
| 超时时间 | 5 秒 |
| 重试次数 | 3 次 |

---

### 5.2 维度：设备资源（满分 20 分）

#### 子项定义

| 子项编号 | 子项名称 | 权重 | 分数池 | 阈值 | 扣分系数 | 数据来源 |
|----------|----------|------|--------|------|----------|----------|
| B-01 | CPU 利用率 | 40% | 8 分 | 90% | 0.8 分/% | SNMP/Telemetry |
| B-02 | 内存利用率 | 40% | 8 分 | 90% | 0.8 分/% | SNMP/Telemetry |
| B-03 | 温度 | 20% | 4 分 | 场景相关 | 0.4 分/°C | SNMP/Telemetry |

#### 温度阈值（按场景）

| 场景 | 默认阈值 | 可配置范围 |
|------|----------|-----------|
| 数据中心 | 75°C | 60°C - 85°C |
| 园区 | 70°C | 55°C - 80°C |
| 光传输 | 65°C | 50°C - 75°C |

#### 扣分公式

**子项 B-01：CPU 利用率（分数池 8 分）**
```
IF CPU利用率 <= 90% THEN
    B01_扣分 = 0
ELSE
    B01_扣分 = min(8, (CPU利用率 - 90) × 0.8)
END IF
```

**子项 B-02：内存利用率（分数池 8 分）**
```
IF 内存利用率 <= 90% THEN
    B02_扣分 = 0
ELSE
    B02_扣分 = min(8, (内存利用率 - 90) × 0.8)
END IF
```

**子项 B-03：温度（分数池 4 分）**

### 5.3 维度：接口状态（满分 20 分）

#### 预期内应 Up 的接口定义

**包含**：
- 已配置 IP 地址的接口
- 已加入业务 VLAN 的接口
- 已通过 LLDP/CDP 检测到邻居的接口
- 配置描述中包含业务关键字的接口

**排除**：
- 未使用的端口（未配置 IP、未加入 VLAN、无描述）
- 管理性 Shutdown 的端口（admin-status = down）
- 预留端口（描述包含 "reserved"、"spare" 等）
- 堆叠端口、管理端口

#### 扣分公式

**子项 C-01：接口 Down（分数池 12 分）**
```
Down接口数 = 预期内应Up的接口中，oper-status = down 的数量
C01_扣分 = min(12, Down接口数 × 2)
```

**子项 C-02：接口错误率（分数池 8 分）**
```
单接口错误率 = (InputErrors + OutputErrors + CRCErrors) / 总包数 × 100%
平均错误率 = Σ(各接口错误率) / 接口数
C02_扣分 = min(8, 平均错误率 × 80)
```

**维度扣分**
```
维度扣分 = C01_扣分 + C02_扣分
设备维度评分 = max(0, 20 - 维度扣分)
```

| C-02 | 0.5 × 80 = 40 → min(8, 40) = 8 | 8 |
| **合计** | — | **10** |

设备维度评分 = 20 - 10 = **10 分**（满分20分）

**示例 2：0 个接口 Down，平均错误率 0.1%**

| C-02 | 0.1 × 80 = 8 | 8 |
| **合计** | — | **8** |

| CPU 利用率 | 90% | SNMP / Telemetry | > 阈值 | 超出 × 0.8 分/%，上限 8 分 |
| 内存利用率 | 90% | SNMP / Telemetry | > 阈值 | 超出 × 0.8 分/%，上限 8 分 |
| 温度 | 场景相关 | SNMP / Telemetry | > 阈值 | 超出 × 0.4 分/°C，上限 4 分 |

**温度阈值参考**：

| 场景 | 阈值 |
|------|------|
| 数据中心 | 75°C |
| 园区 | 70°C |
| 光传输 | 65°C |

**说明**：此维度合并了 Cisco 的 CPU(20%)、内存(20%)、电源/风扇(10%)、温度(10%) 四个 KPI。

#### 维度三：接口状态（满分 20 分，对齐 Cisco "链路"权重 40%）

| 检查项 | 异常条件 | 扣分规则 |
|--------|----------|----------|
| 接口 Down | 有预期内应 Up 的接口处于 Down 状态 | 每个 × 2 分，上限 12 分 |
| 接口错误率 | 错误率 > 1% | 错误率 × 80，上限 8 分 |

**预期内应 Up 的接口**：
- 已配置且未管理性关闭的接口
- 已连接设备或链路的接口
- 排除：未使用的端口、管理性 Down 的端口、预留端口

**接口错误率计算**：
```
错误率 = (Input Errors + Output Errors + CRC Errors) / 总包数 × 100%
```

#### 维度四：协议状态（满分 20 分，v2.0）

| 检查项 | 异常条件 | 扣分规则 |
|--------|----------|----------|
| BGP 会话 | 有 BGP 会话非 Established | 每个 × 2 分，上限 8 分 |
| EVPN 会话 | 有 EVPN 会话非 Established | 每个 × 2 分，上限 8 分 |
| OSPF 邻居 | 有 OSPF 邻居非 Full | 每个 × 1 分，上限 4 分 |

**检查范围**：
- 仅检查预期应有的会话（如 Leaf 到 Spine 的 BGP）
- 不检查未配置的会话

#### 维度五：业务指标（满分 20 分，v2.0）

**数据中心 AIDC**：

| 检查项 | 阈值 | 扣分规则 |
|--------|------|----------|
| ECN 标记率 | 1% | 超出 × 7 分/1%，上限 7 分 |
| PFC 暂停频率 | 100/min | 超出 /10 × 0.7 分，上限 7 分 |
| Buffer 利用率 | 80% | 超出 × 0.6 分/%，上限 6 分 |

**园区**：

| 检查项 | 阈值 | 扣分规则 |
|--------|------|----------|
| AP 覆盖率 | 90% | 低于 × 2 分/%，上限 20 分 |
| 漫游成功率 | 90% | 低于 × 2 分/%，上限 15 分 |
| 认证成功率 | 95% | 低于 × 2 分/%，上限 15 分 |

**光传输**：

| 检查项 | 阈值 | 扣分规则 |
|--------|------|----------|
| OSNR | 18dB | 低于 × 5 分/dB，上限 25 分 |
| BER | 1e-9 | log10(比) × 10 分，上限 20 分 |

### 4.3 v1.0 判定规则汇总

**计算模型**：各维度独立扣分，汇总后判定状态（对齐 Cisco）

| 维度 | 子项 | 扣分条件 | 扣分规则 | 扣分上限 |
|------|------|----------|----------|----------|
| 设备可用性 | 可达性 | 离线 | 20 分 | 20 分 |
| 设备资源 | CPU | > 90% | 超出 × 0.8 分/% | 8 分 |
| 设备资源 | 内存 | > 90% | 超出 × 0.8 分/% | 8 分 |
| 设备资源 | 温度 | > 阈值 | 超出 × 0.4 分/°C | 4 分 |
| 接口状态 | 接口 Down | 有预期内接口 Down | 每个 × 2 分 | 12 分 |
| 接口状态 | 接口错误率 | > 1% | 错误率 × 80 | 8 分 |

**设备状态判定**：
- 健康：设备健康度 ≥ 90 分（所有维度正常或轻微扣分）
- 亚健康：设备健康度 70-89 分（部分维度扣分）
- 不健康：设备健康度 < 70 分（设备离线或严重扣分）

### 4.4 判定流程图

```
                    ┌─────────────┐
                    │  开始计算   │
                    └──────┬──────┘
                           ↓
              ┌────────────────────────┐
              │  维度一: 设备可达性     │
              └────────────┬───────────┘
                           ↓
              ┌────────────────────────┐
              │      设备是否在线？     │
              └────────────┬───────────┘
                    ┌──────┴──────┐
                    ↓             ↓
                ┌───────┐    ┌───────┐
                │ 不健康 │    │ 在线  │
                │(0 分)  │    └───┬───┘
                │(停止)  │        ↓
                └───────┘   ┌─────────────────────────────────┐
                            │  并行计算以下维度（互不影响）    │
                            │  ├─ 维度二: 设备资源            │
                            │  ├─ 维度三: 接口状态            │
                            │  ├─ 维度四: 协议状态（v2.0）    │
                            │  └─ 维度五: 业务指标（v2.0）    │
                            └──────────────┬──────────────────┘
                                           ↓
                            ┌─────────────────────────────────┐
                            │  汇总各维度扣分                  │
                            │  设备健康度 = 100 - Σ扣分       │
                            └──────────────┬──────────────────┘
                                           ↓
                            ┌─────────────────────────────────┐
                            │  判定设备状态                    │
                            │  ≥ 90: 健康                     │
                            │  70-89: 亚健康                  │
                            │  < 70: 不健康                   │
                            └─────────────────────────────────┘
```

**与 Cisco 对照**：
- Cisco 采用各 KPI 并行检查后加权聚合
- 本方案采用各维度并行检查后汇总扣分
- 两者本质相同：各检查项独立计算，互不影响

## 13. 因果关系处理

### 13.1 问题场景分析

| 场景 | 因果关系 | 原方案问题 | 本方案处理 |
|------|----------|-----------|-----------|
| 设备离线 | 离线必然产生告警 | 告警 + 离线同时扣分 | 离线时其他维度不计算，告警独立展示 |
| CPU 超阈值 | 可能导致协议震荡 | CPU + 协议同时扣分 | 并列扣分，反映问题叠加 |
| 接口 Down | 必然产生告警 | 接口 + 告警同时扣分 | 接口扣分，告警独立展示 |
| 光功率异常 | 可能导致 BER 升高 | 光功率 + BER 同时扣分 | 并列扣分，两个独立问题 |

### 13.2 处理原则

**原则一：告警不参与健康度计算**
- 告警有独立的功能模块展示
- 健康度反映设备客观运行状态
- 避免因果关系导致的重复扣分

**原则二：设备离线特殊处理（对齐 Cisco）**
- 设备离线时，可用性维度 = 0 分
- 其他维度不计算，按 0 分参与权重计算
- 这是一种"一票否决"机制，符合 Cisco "不可达直接判定 Poor" 的逻辑

**原则三：其他维度并行计算（对齐 Cisco）**
- Cisco 采用各 KPI 独立评分后加权聚合
- 本方案采用各维度独立扣分后汇总
- 并行计算能反映问题的叠加效应，不会因为一个维度异常而停止其他维度检查

### 13.3 与友商方案对比

| 厂商 | 因果处理方式 | 优点 | 缺点 |
|------|-------------|------|------|
| Cisco | 各 KPI 独立评分后聚合，可达性优先 | 简单直观，逻辑清晰 | — |
| Juniper | Classifier 分层，上层覆盖下层 | 逻辑清晰 | 停止检查可能遗漏问题 |
| 华为 | 未处理 | — | 存在重复扣分 |
| **本方案** | 对齐 Cisco：告警独立 + 设备离线特殊处理 + 其他维度并行计算 | 逻辑清晰，避免重复扣分，反映问题叠加 | — |

## 14. 版本演进路径

### 14.1 演进原则

| 原则 | 说明 |
|------|------|
| 模型不变 | 三层架构（子项扣分 → 维度评分 → 站点健康度）保持不变 |
| 增量增加 | 新版本增加检查项，不改变已有检查项 |
| 权重可调 | 维度权重可根据场景调整 |
| 平滑演进 | 用户升级后能理解分数变化 |

### 14.2 演进路线

```
v1.0 基础版
├── 维度：可用性 + 资源 + 接口
├── 权重：40% + 30% + 30%
└── 适用：三场景通用

        ↓ 增量演进

v2.0 增强版
├── 维度：v1.0 + 协议 + 业务指标
├── 权重：按场景定制
└── 适用：
    ├── 数据中心：+ BGP/EVPN + ECN/PFC/Buffer
    ├── 园区：+ AP 状态 + 覆盖率/漫游/认证
    └── 光传输：+ 光功率/保护 + OSNR/BER

        ↓ 规划演进

v2.1 智能版（规划）
├── 动态基线（参考 Arista CUE）
├── AI 预测性分析
└── 异常根因定位
```

### 14.3 升级影响

| 升级路径 | 模型变化 | 分数变化 | 用户理解成本 |
|----------|----------|----------|-------------|
| v1.0 → v2.0 | 增加维度 | 可能下降（更多检查项） | 低（增量增加） |
| 设备分类 → 维度扣分 | 完全改变 | 无法对比 | 高（需重新理解） |

**本方案选择**：增量演进，用户升级后能清楚知道"因为增加了协议和业务检查，所以分数可能下降"。
